# CLAUDE_EN.md – Guide for the AI assistant (Badminton Board, STM32F030)

This file describes the context, rules and technical notes of the project. Read it carefully before writing or changing code. Vietnamese version: `CLAUDE.md` (the two files must always have equivalent content).

Related documents: `README.md` (hardware settings, function list), `plan.md` (step-by-step plan), `docs/coding_style.md` (naming and formatting conventions).

---

## 1. Project overview

A badminton reaction-training device: position LEDs light up at random, the player touches/presses the matching position, results are shown on a 7-segment display, and there is a buzzer. One master controls up to 6 slaves over nRF24L01.

- MCU: **STM32F030** (Cortex-M0, 48 MHz). Exact part number: **not decided yet**.
- IDE: **STM32CubeIDE** (configured through the `.ioc` file).
- Language: **C**.
- Debug: USART1 at 115200 baud.
- No soft PWM and no LED fade effect. LEDs are on/off only.

## 2. Key hardware settings (summary)

| Item | Value |
|---|---|
| Clock | HSI through PLL, SYSCLK/HCLK **48 MHz**, APB1 /1, timer clock 48 MHz |
| SysTick | 1 kHz |
| UART | USART1, **PA9 TX / PA10 RX**, 115200 8N1, DMA TX Normal, DMA RX **Circular** |
| SPI | SPI1, **PA5 SCK / PA6 MISO / PA7 MOSI**, Master, mode 0, 8-bit MSB first, NSS software, prescaler **8** (6 Mbps) |
| TM1637 | **PA1 = CLK, PA2 = DIO**, Open Drain, Pull-up (bit-banged, not I2C) |
| TIM16 | 1 kHz (PSC 47, ARR 999): scheduler tick |
| TIM17 | Free-running 1 MHz counter (PSC 47, ARR 65535): `Bsp_DelayUs()` |
| ADC | 12 bit; speed 20 steps (205 counts/step), time 59 steps (70 counts/step) |
| nRF24L01 | Channel 77 to 80, 2 Mbps, 2-byte CRC, dynamic payload, ACK payload, ARD 750 µs, ARC 3 |

Pins still **TBD**: `NRF_CSN`, `NRF_CE`, `NRF_IRQ`, buttons, position LEDs, buzzer, ADC pin. See `README.md` for details.

## 3. Directory structure and layering

```
firmware/main_board/
├─ Core/      generated by Cube, DO NOT edit outside USER CODE blocks
├─ Drivers/   HAL, LL, CMSIS (managed by Cube)
├─ App/       application logic (Inc/, Src/)  - hardware-agnostic
├─ Bsp/       hardware drivers (Inc/, Src/)
└─ main_board.ioc
```

Layering: `App -> Bsp -> Core/Drivers (HAL, LL) -> Hardware`.

- `App` **only calls `Bsp`**; it must not include HAL/LL headers or touch registers.
- `Bsp` contains no business logic.
- `led7.c` and `led.c` only write into the frame buffer of `tm1637.c`; `tm1637.c` sends the whole frame when something changed.
- Do not give files the same name as Cube-generated files (`adc.c`, `usart.c`, `spi.c`, `tim.c`, `gpio.c`): use `bsp_adc.c`, `uart_comm.c`, and so on.
- Project code lives in `App/` and `Bsp/`, **never inside `Core/`**.
- `App/` and `Bsp/` must be registered in CubeIDE (Source Location and Includes), otherwise the files are not compiled.

## 4. Mandatory rules

### Do
1. **Write only between `USER CODE BEGIN/END` pairs** when editing Cube-generated files (`main.c`, `stm32f0xx_it.c`, ...). Code outside the blocks is lost when code is regenerated.
2. **Every public function, struct, enum and macro has a Doxygen comment** (see section 6).
3. Every wait loop (SPI, CE, DMA, flags) must have a **timeout**.
4. Variables shared with an ISR must be **`volatile`**.
5. Use fixed-width types: `uint8_t`, `uint16_t`, `uint32_t`.
6. Name constants with `#define`/`enum` and state the **unit** (for example `step_time_100ms`, `run_time_s`).
7. Functions and variables used only inside one file are **`static`**.
8. Check array bounds and division by zero before use.
9. Check the return value of any function that can fail.
10. Set User Labels for pins in the `.ioc` and use the `XXX_Pin`, `XXX_GPIO_Port` macros; do not hard-code `GPIOx`/`GPIO_PIN_x`.

### Do not
1. Do not edit anything in `Drivers/`.
2. Do not call `Log_Printf`, `printf`, `HAL_Delay` or long blocking functions **inside an ISR**.
3. Do not use `printf("%f")` (costs too much flash on the F030).
4. Do not use `%` or division in an ISR when avoidable (Cortex-M0 has no hardware divide).
5. Do not leave magic numbers in code.
6. Do not define the same HAL callback (`HAL_..._Callback`) in several files: define each callback **once** and distinguish by `Instance`.
7. Do not assume information that is still TBD (see section 9); ask instead.
8. Do not reintroduce soft PWM or LED fading.

## 5. Naming conventions (summary)

| Kind | Convention | Example |
|---|---|---|
| File | `snake_case`, lowercase | `uart_comm.c` |
| Public function | `Module_Action()` | `Uart_RxRead()`, `Nrf_Send()` |
| Internal function | `static`, `snake_case` | `static uint8_t spi_xfer(uint8_t tx)` |
| Global variable | `g_` prefix | `g_app_state` |
| File-scope `static` variable | `s_` prefix | `s_rx_tail` |
| Macro / constant | `UPPER_SNAKE_CASE` | `RX_DMA_SIZE` |
| Enum | `MODULE_NAME_VALUE` | `APP_STATE_RUN` |
| Type | `_t` suffix | `nrf_pkt_t` |
| Boolean | `is_`, `has_` | `is_locked` |

Headers always have include guards. Details: `docs/coding_style.md`.

## 6. Doxygen comment standard

All new code must have Doxygen comments. Use the `/** ... */` style with `@` commands. Comment language: **English** (suggested; switch to Vietnamese only if the team agrees, and then keep it consistent across the whole project).

### 6.1. File header (`.c` and `.h`)

```c
/**
 * @file    uart_comm.c
 * @brief   UART receive driver using circular DMA.
 * @details Received bytes are written by DMA into a ring buffer and read
 *          by the main loop with Uart_RxRead().
 * @author  <author name>
 * @date    <yyyy-mm-dd>
 */
```

### 6.2. Functions (in the `.h` for public functions, in the `.c` for `static` ones)

```c
/**
 * @brief   Read one byte from the UART receive buffer.
 * @details Non-blocking. Must be called from one context only (main loop),
 *          because it modifies the read pointer.
 *
 * @param[out] byte  Pointer that receives the byte read. Must not be NULL.
 *
 * @retval 1  A byte was read and stored in @p byte.
 * @retval 0  The buffer is empty; @p byte is unchanged.
 *
 * @note    Call often enough: the 256-byte buffer fills in about 22 ms
 *          at 115200 baud.
 * @warning Do not call from an ISR.
 */
uint8_t Uart_RxRead(uint8_t *byte);
```

Rules:
- `@brief` is mandatory: one sentence, starting with a verb.
- `@param[in]`, `@param[out]` or `@param[in,out]` for **every** parameter, with the **unit** and limits (for example "unit: 100 ms, range 5..100").
- `@return` (or `@retval` per value) for functions that return something.
- `@note` and `@warning` for calling conditions, ISR/timing constraints and side effects.
- `@see` to point to related functions when useful.

### 6.3. Structs, enums, macros, variables

```c
/** @brief Message types of the nRF network protocol. */
typedef enum {
    MSG_NONE = 0,    /**< No message. */
    MSG_POLL,        /**< Master -> slave: poll only. */
    MSG_SET_TARGET   /**< Master -> slave: light the target LED. */
} msg_type_t;

/** Number of bytes in the UART receive DMA buffer. */
#define RX_DMA_SIZE  256U

static volatile uint16_t s_rx_tail;  /**< Next read index, main loop only. */
```

### 6.4. Module groups (optional)

```c
/** @defgroup BSP_UART  UART debug and receive
 *  @{ */
/* ... declarations ... */
/** @} */
```

### 6.5. When to update comments
- When a signature, unit, calling condition or behavior changes, **update the comment in the same commit**.
- Do not write comments that repeat the statement; explain **why** and the constraints.

## 7. Main modules and public functions

### UART debug (`Bsp/bsp_log`, `Bsp/uart_comm`, `App/cmd`)

| Function | Role |
|---|---|
| `Log_Write`, `Log_Printf`, `LOG_E`, `LOG_I` | Send logs through a ring buffer + DMA, non-blocking; drops data when full |
| `Uart_RxStart`, `Uart_RxAvailable`, `Uart_RxRead`, `Uart_RxOverflowTaken` | Receive through circular DMA; overflow detected by counting DMA laps |
| `cmd_feed`, `cmd_execute`, `cmd_reset` | Assemble command lines (state kept between calls) and run debug commands |

The main loop drains at most 32 bytes per pass, and calls `cmd_reset()` when `Uart_RxOverflowTaken()` returns 1.

### SPI / nRF24L01 (`Bsp/nrf24`, `App/net_proto`)

| Group | Functions |
|---|---|
| Registers | `Nrf_ReadReg`, `Nrf_WriteReg`, `Nrf_ReadRegBuf`, `Nrf_WriteRegBuf`, `Nrf_ReadStatus`, `Nrf_ClearFlags`, `Nrf_FlushTx`, `Nrf_FlushRx`, `Nrf_SelfTest` |
| Configuration | `Nrf_Init`, `Nrf_SetChannel`, `Nrf_SetTxAddr`, `Nrf_SetRxAddr`, `Nrf_EnterTx`, `Nrf_EnterRx` |
| Send/receive | `Nrf_Send`, `Nrf_ReadPayloadWidth`, `Nrf_Receive`, `Nrf_WriteAckPayload`, `Nrf_GetLostCount` |
| Network | `Net_Init`, `Net_Task`, `Net_SetTarget`, `Net_Stop`, `Net_IsOnline`, `Net_OnHit` |

Of these, `Nrf_ReadReg`, `Nrf_WriteReg` and `Nrf_SelfTest` already have sample code; the rest are proposals and are not written yet.

Packet: 4-byte header (`type`, `node_id`, `seq`, `len`) + payload ≤ 28 bytes (32 total). `MSG_SET_TARGET` has **no** `brightness` field.

## 8. Technical pitfalls

### Chip and clock
- **The F030 has no TIM2 and no TIM4.** Usable timers: TIM1, 3, 14, 15, 16, 17 (some parts also have TIM6, 7).
- F0 does not have the F1/F4-style `HAL_RCC_GetPCLK2Freq()`; take the timer clock from APB1.
- If the APB1 prescaler is not /1 the timer clock is doubled: recompute all prescalers.
- PA1 is ADC1 channel (possible conflict with `TM_CLK`). PA0 to PA7 must only see **3.3 V**.

### SPI and nRF24L01
- The nRF24 SPI limit is 10 Mbps: **never use prescaler 4** (12 Mbps).
- With LL in 8-bit mode on F0: set the RX FIFO threshold to 1/4, otherwise RXNE never rises and the code hangs.
- **Keep CSN low for the whole command**, then raise it. The first byte the nRF returns is always `STATUS`.
- Clear `STATUS` flags by **writing 1** to the bit.
- On `MAX_RT`: clear the flag **and `FLUSH_TX`**, otherwise the TX FIFO stays stuck.
- Before polling a slave: set `TX_ADDR` **and** `RX_ADDR_P0`.
- The slave must load its ACK payload **before** the next poll (the master receives it one poll later).
- The slave **measures the reaction time itself** and reports it, because radio latency would distort it.
- Wait ≥ 100 ms after power-up before talking to the module. **3.3 V** supply, capacitor next to VCC.
- Default values to verify SPI: `CONFIG = 0x08`, `SETUP_AW = 0x03`, `RF_CH = 0x02`.

### UART and DMA
- The 256-byte RX buffer fills in about **22 ms** at 115200. If the reader is slow, DMA **overwrites data without any error**.
- Comparing two pointers alone **cannot tell full from empty**: count DMA laps.
- `Uart_RxRead` must be called from **one place** only.
- The default DMA channels of USART1 collide with SPI1: remap if SPI ever uses DMA.

### TM1637
- The protocol looks like I2C but **is not I2C** (no address, LSB first): bit-bang with GPIO.
- Half period about 3 to 5 µs. Send only when data changed (each update takes about 1 ms).

### HAL and LL
- Function interfaces are the same for HAL and LL; only the internals differ.
- With LL: **clear interrupt flags yourself** in `xxx_IRQHandler`; there are no HAL callbacks.
- Default: **HAL** (without soft PWM there is no high-frequency interrupt left). The final library choice is not decided, see section 9.

### Application (`app.c`)
- Units: step time is in **100 ms** units, training time is in **seconds** (uint16_t, max 300).
- Start with no position selected: buzzer error, **do not run** (avoids division by zero in `rand() % count`).
- `App` must not use `HAL_GetTick()`; use `Bsp_Millis()`.

## 9. Open decisions (ask, do not assume)

1. Exact F030 part number.
2. Position LEDs on the TM1637 (shared brightness) or on MCU GPIO (on/off).
3. The TBD pins (section 2) and the ADC pin.
4. Library: HAL, LL or mixed.
5. Whether slaves have a 7-segment display and buzzer or only LEDs and a touch sensor.
6. Use the nRF24 IRQ right away or start with polling (recommended: polling first).
7. Whether to use the watchdog and store settings in flash.
8. Language of code comments (suggested default: English).

When data from these items is needed, **ask the user** instead of guessing.

## 10. Workflow

1. Read `README.md` and `plan.md` to know the current phase.
2. **Commit to Git before every CubeMX Generate Code.**
3. Work in small modules, verify each one, then integrate.
4. After writing code: check the points in section 4, complete Doxygen comments, build with no warnings (`-Wall -Wextra`).
5. If hardware settings or function interfaces change, update **all of** `README.md`, `plan.md`, `CLAUDE.md` and `CLAUDE_EN.md`.
6. When editing a Cube-generated file, state which `USER CODE` block was changed.
7. Reply in the **user's language** (Vietnamese by default); function names, variables and code comments follow sections 5 and 6.
8. If a request conflicts with the rules in section 4, point out the problem and propose an alternative instead of silently complying.
